## Python 代码风格与实现规范

本项目的 Python 代码以核心框架稳定、职责清晰、长期可维护为目标，同时服务于研究导向的快速迭代。代码应避免腐化，但也不应过早引入复杂兜底、过度抽象或生产级防御逻辑。

### 1. 总体原则

- 核心框架代码应优先保证稳定性、可维护性和清晰边界。
- 研究/实验脚本可以更灵活，服务于快速验证，但不得将临时代码、硬编码路径、调试逻辑或不稳定接口扩散到框架层。
- 默认采用最小修改原则：只完成用户明确要求的内容，不要在没有明确指示的情况下顺手重构、扩展功能或提前实现“可能会用到”的能力。
- AGENTS.md 中的 Python 规范属于强约束。除非用户明确要求或当前任务确实需要，否则应严格遵守。

### 2. 修改边界

- 需求存在歧义时，应先确认，尤其是会影响接口、职责边界、架构方向或长期维护性的歧义。
- 如果发现相邻代码存在问题但不属于本次任务范围，应在回复中指出，不要直接修改。
- 可以按合理模块边界修改多个文件，但修改范围必须服务于当前任务。
- 如果当前任务暴露出架构级重构需求，应先在现有基础上完成当前目标，再提出重构方案供用户确认，不要直接大规模重构。
- 当存在多种实现方案时：
  - 局部实现细节可以选择最小、清晰、符合现有风格的方案直接实现。
  - 涉及接口设计、模块职责、数据结构、外部依赖、长期扩展点或架构方向的选择，必须先给出方案比较并等待确认。
  - 如果已有稳定的平行实现，应优先遵循现有范式。

### 3. 类型标注与接口

- 公共接口、核心类和复杂函数应使用 type hints。
- 函数返回值应显式标注，包括 `-> None`。
- 当前阶段允许适度使用 `Any`、`dict[str, Any]` 等弱类型，尤其是在设计尚未稳定时。
- 核心接口应尽量保持语义清楚；当数据结构稳定后，应逐步迁移为 `dataclass`、`TypedDict`、`Protocol` 或明确的类型别名。
- 不强制所有内部小函数都写完整类型标注，但不得因此影响核心接口可读性。

### 4. 函数、类与抽象

- 框架代码中的函数应尽量短小、职责单一；业务逻辑函数可以适当更长，但必须分段清楚，保持单一职责。
- 可以设计抽象基类、接口或插件机制，但抽象必须来自明确的职责划分或确定的扩展需求。
- 避免 speculative abstraction / speculative implementation。不要为了未来可能出现的需求提前实现复杂机制。
- 对于确定会扩展的核心扩展点，应主动设计稳定接口，而不是等后续反复推倒重来。
- 谨慎抽取通用工具函数。只有重复出现、语义稳定、确实能降低维护成本时才抽取。

### 5. 命名

- 命名应以清晰语义为主。
- 允许常见领域缩写，例如 `obs`、`env`、`cfg`、`traj`、`ckpt`、`repo`。
- 避免生造缩写、过短变量名和只有作者自己能理解的命名。
- 简单局部变量可以简短，但跨模块、跨函数传递的变量应具有明确语义。

### 6. 注释与 Docstring

- 注释应服务于理解成本较高的地方，解释设计意图、算法逻辑、特殊处理、隐含假设或容易踩坑的行为。
- 避免解释显而易见的代码。
- 注释应简洁，不要连续堆叠大量注释造成阅读负担。
- 公共接口、抽象类和复杂函数应写简洁 docstring；内部简单函数可以省略。
- 注释和 docstring 主要使用中文；同一文件内尽量保持语言一致。
- 代码相关术语可以保留英文，例如 `registry`、`type hints`、`fail fast`、`smoke test`。

### 7. 错误处理与防御性编程

- 默认 fail fast。遇到不符合预期的状态时，应尽早抛错，而不是静默 fallback 或吞掉问题。
- 非必要情况下少用 `try/except`。
- 禁止裸 `except`。
- 如果必须捕获异常，应捕获明确异常类型，并保留足够上下文，方便定位问题。
- 不要用宽泛异常、静默失败或返回模糊的 `None` 来掩盖真实错误。
- 允许添加少量关键断言和边界检查，例如 shape、路径存在性、配置字段、状态合法性等。
- 不要为了“保险”堆叠大量 fallback、兼容分支或兜底代码。

### 8. 配置、常量与依赖

- 配置管理按场景选择。默认可以使用 YAML 作为实验/运行配置。
- 当配置需要类型约束、默认值、校验逻辑或组合构造时，可以使用 `dataclass` 或 Python 配置类。
- 核心代码禁止硬编码关键路径、设备名、seed、重要超参数和 magic number。
- 一次性实验脚本可以少量硬编码，但不得污染框架代码。
- 不反对引入外部依赖。如果需求已经到了需要成熟库支持的程度，应优先考虑可靠库，避免重复造轮子。
- 环境中已有依赖可以直接使用。
- 未安装的新依赖需要先说明用途、收益和替代方案，再与用户讨论是否引入。

### 9. 格式化、测试与验证

- 不要求每次小改动都立即运行完整格式化流程。
- 当工作完成一个边界较清晰的阶段后，再集中进行风格统一、格式整理和必要的 lint。
- 可以使用 `ruff`、`black`、`isort` 等工具，但不要让格式问题打断早期开发节奏。
- `pytest` 按需使用。
- 不要求所有改动都测试；涉及核心逻辑、接口变更、较大更新或可能引入风险的改动时，应补充最小测试或 smoke test。
- agent 不必每次修改后都说明验证方式，除非修改本身具有风险或用户明确要求。

### 10. 实验、日志与可复现性

- 实验入口应显式支持 seed 配置。
- 涉及实验、采样、数据划分、模型调用扰动等场景时，应统一设置 `random`、`numpy`、`torch` 等相关 seed。
- 训练/实验代码应记录关键指标，例如 loss、reward、learning rate、grad norm、checkpoint path、配置文件路径、实验输出目录等。
- 框架代码使用 `logging`。
- 实验脚本、一次性脚本可以使用 `print`。
- 不要在框架代码中长期保留临时 debug 输出。

### 11. Tensor、device 与 ML/RL 相关代码

- 如果涉及 ML/RL 代码，核心张量流应尽量明确 shape、dtype 和 device 约定。
- 复杂 reshape、batch/sequence 维度变化、跨模块传递的 tensor，应添加必要注释或 assert。
- 不要过度标注简单张量操作。
- 禁止到处散落 `.cuda()`；应使用统一的 `device` 管理。
- tensor 创建时应考虑 device 和 dtype 的一致性。

### 12. 文件组织与模块依赖

- 文件职责按复杂度决定，不强制“一文件一类”或“一文件一职责”。
- 同一文件内的内容应保持较高语义相关性，避免把无关逻辑堆在一起。
- 允许新增文件，只要新文件职责明确，并且服务于当前任务。
- 模块依赖应尽量保持清晰分层。
- 核心模块应避免循环依赖、反向依赖和跨层滥用 import。
- 当需要从某个模块集中导入大量同类符号时，允许使用 `from ... import *`，但不作为默认写法。
- `import *` 应限制在语义清晰的场景，例如 constants、registry、public API re-export 等，避免让依赖来源变得不可追踪。

### 13. Registry 与全局状态

- 避免普通全局可变状态，优先通过显式传参、对象持有状态或依赖注入来降低排查难度。
- 允许 registry 机制，但仅用于明确会扩展的框架级组件，例如 mutator、evaluator、optimizer、runner backend 等。
- registry 应集中管理、职责清楚，只负责注册和查找实现，不应承载复杂业务逻辑。
- 不要让 registry 变成隐式全局状态容器。
- 如果当前只有一个实现，且没有明确扩展需求，不应为了抽象而引入 registry。

### 14. Python 惯用写法

- 核心代码优先使用现代 Python 惯用写法，例如 `pathlib.Path`、`dataclass`、`Enum`、`Protocol`、类型别名等。
- 允许使用现代类型语法，例如 `dict[str, Any]`、`Path | None`。
- 谨慎使用较新的控制流语法，例如 `match/case`；只有在它能明显提升表达清晰度时才使用。
- 公共 API 暂不强制整理，不必一开始就大量维护 `__all__` 或复杂的 `__init__.py` re-export；等模块边界稳定后再统一整理。

### 15. 实现完整度与临时代码

- 如果当前模块没有类似或平行实现，默认先实现核心路径，保证主流程清晰、可运行、易理解。
- 如果已有稳定的同类实现，进行平行扩展时应遵循现有写法，包括接口风格、文件组织、命名、日志、配置方式等。
- 尽量不留下 TODO 或 placeholder。
- 只有确定未来会实现、但当前阶段明确不做的内容，才允许留下 TODO 或 placeholder。
- TODO 应写清楚原因和后续预期，不要留下模糊的“后面再说”。
- 未验证的新实现可以短期使用临时 debug 代码，但最终提交前应删除，或收敛为正式日志、断言或测试。
- 按已有稳定范式扩展或修正问题时，非调试情况下应尽量避免插入临时 debug 代码。

### 16. 可读性与性能

- 可读性优先于代码行数。
- 简单表达式可以简洁写；复杂逻辑不要压成一行式、深层嵌套推导式或过长链式调用。
- 不提前做性能优化。先保证思路正确、结构清晰、代码可理解。
- 当完成一个边界清晰的阶段后，再集中考虑性能优化、格式统一和代码整理。
- 对明显低效且容易修正的问题，可以在不影响主逻辑和修改范围的前提下处理。
