## 5. 待核验主张

### CLAIM-H1：Pre-materialization Evidence Gate

冻结真实 Student Prefix 后，repeated matched no-op continuation 与不可部署 soft-intervention continuation 产生的局部证据，能够预测下游 Candidate effect，并在硬预算匹配下提高 useful Candidate yield、减少无效完整评估。

### CLAIM-H2A：Student Realizability Prediction

对 Student-owned recognition、decision、adherence、fallback 与 parse responsibility 的独立 probe，能够预测未参与 probe 的 Prefix 上 shadow/in-loop 真实可执行性。

### CLAIM-H2B：Student-aware Routing

基于 H2A 在 reject、simplify、deterministic lowering 与 ownership reassignment 之间路由，相对 always-Student、always-deterministic 与无 feasibility routing，提高可实现/有用 Candidate 产出并减少浪费。

### CLAIM-H3：Verification-grounded Role-scoped Experience

在冻结 H1/H2 后，将全部有研究意义的 typed verdict 与终态转为有 provenance、严格 consumer/scope、可失效和可复查的 optimizer experience，能够相对 no-memory、global/shared、generic role-local、DREvo-like 与 Auto-Robotist-like memory 减少能力越界提案、同角色 obligation 复发和方向重复，并提高 useful Candidate yield per budget，同时控制 false pruning 与 held-out utility。

## 6. 候选验证协议

### EVAL-H1：Matched Prefix + Blind Candidate Audit

- 真实 rollout 仅提供 Prefix。
- 在同 Prefix、同 Student/config 下随机化执行 repeated no-op 与 soft-intervention 两臂。
- Trial Selector、intervention contract、process outcome 与 task outcome 冻结。
- 对预注册比例的 Gate-rejected mechanism 仍做盲编译和完整 Candidate evaluation，以估计 false rejection。
- 产物：Prefix manifest、双臂 continuation、trial review、gate decision、blind compiler input、Candidate effect 与 cost ledger。

### EVAL-H2A：Responsibility Probe / Shadow In-loop Validation

- 使用与 probe 构建集不重合的 Prefix。
- 分别标注 recognition、decision、adherence、fallback、parse failure。
- 比较 probe prediction 与 shadow/in-loop observation；不得用最终 Candidate accuracy 代替职责级标签。

### EVAL-H2B：Routing Strategy Comparison

- 对同一 evidence-backed mechanism portfolio 比较 always-Student、always-deterministic、no-feasibility-routing 与 adaptive routing。
- 保存 ownership/lowering decision、实现结果、conformance、Candidate effect 和总成本。

### EVAL-H3：Frozen-pipeline Multi-episode Evolution

- 先验证并冻结 H1/H2 标签、Gate 与实现。
- 各 memory condition 从相同 cold start、任务块、Teacher/Student 配置和配对 seed 开始，使用独立 Store。
- 正式比较 no-memory、global/shared、generic role-local、ExpeL/G-Memory-style、DREvo-like、Auto-Robotist-like、完整 H3，以及 provenance/scope/invalidation/bypass/component 消融。
- 每次 Researcher 调用保存 blinded proposal shortlist 与 memory-conditioned shortlist；固定概率抽取被压制方向走完整旁路，估计 false pruning。
- 计量单位同时包括 settled optimizer episodes、experience write/retrieval opportunities、token、rollout、full Candidate evaluations 和 complete run/seed。

### EVAL-UTILITY：Frozen HotpotQA Held-out Utility

- train 509 仅用于 research/evolution、Gate audit 和协议开发，三者必须按 manifest 互斥。
- dev 641 完全隔离于 Researcher、Experience Store、机制选择和阈值调整；只对冻结系统与关键基线执行最终评测。
- 每 example 3 rollouts；相同 sampling seed/block、Student/Teacher Judge/evaluator/retriever snapshot；报告 accuracy、majority/stability、task/execution failures、Student/hook/Teacher tokens。

## 7. 推荐的验收逻辑（待用户确认）

1. **H1 预测有效性**：blind audit 中 gate-supported 与 gate-rejected mechanisms 的 downstream useful rate/utility ranking 存在正向区分；配对/分层 95% 区间的差异下界大于 0。Gate false-negative point estimate 与区间上界分别不超过待确认的 `α_fn_point` 与 `α_fn_upper`。
2. **H1 系统收益**：H1-only 与 H1+H2 相对 candidate-first 在正式 hard budget `B_run` 下，useful Candidate yield per million all-in tokens 的配对 95% 差异下界大于 0，并减少 full evaluations；held-out utility 非劣界为待确认的 `δ_utility`。
3. **H2A**：职责级 macro-AUROC 的 95% 下界大于 0.5；同时报告每种 responsibility 的 confusion/calibration，不能只用 aggregate 掩盖某一职责完全失效。
4. **H2B**：adaptive routing 相对三种固定策略中最强者的 useful/realizable Candidate yield per budget 配对 95% 差异下界大于 0；held-out utility 非劣界 `δ_utility`。
5. **H3 搜索效率**：完整 H3 相对最近邻中最强者，对 capability-violating proposal、duplicate direction 和 same-role obligation recurrence 的 rate ratio 上界均小于 1；useful Candidate yield per million all-in tokens 的配对 95% 差异下界大于 0。
6. **H3 安全边界**：held-out utility 非劣界 `δ_utility`；false-pruning point estimate 与区间上界不超过待确认的 `α_prune_point`、`α_prune_upper`；stale/corrupted memory 能通过 invalidation、contradiction 或 bypass 恢复。
7. **覆盖与重复**：配对 run seeds 数 `N_seed`、blind portfolio 总机制数 `N_mechanism`、supported/rejected 最低数、failure direction 覆盖数、每 Run settled episodes `N_episode` 和每类 experience retrieval opportunities `N_retrieval` 均需在最终代码冻结后的正式 baseline/power analysis 或用户明确资源政策下预注册。
8. **整体逻辑**：H1、H2A、H2B、H3 分别判定，任一失败只撤回相应贡献。不能用整体最终 accuracy 替代机制证据。若最终 Candidate utility 超过非劣界、发生 split leakage、使用 soft budget 越界结果、或关键配置/数据/Store 无 digest，则整个 Goal 判定不通过。

任何上述数值都不得从当前配置或历史开发 Run 继承。`B_run`、`δ_utility`、误拒/误剪边界和最低覆盖必须引用最终冻结代码上的正式 baseline/power analysis，或由用户明确指定为研究风险政策；确定后先冻结 Goal，再运行方法实验。
