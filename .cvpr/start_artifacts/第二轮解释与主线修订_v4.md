# START-001 第二轮解释与主线修订

状态：吸收三方增量审查后的讨论稿，尚未得到用户最终确认。

## 1. 为什么上一稿没有把 0820_report.md 的核心优势讲清楚

上一稿没有否定这条主线，但我做了三件不利于理解的事。

第一，我把同一研究命题的两道门拆成了两个像是互相竞争的候选：

- IDEA-001R：机制先接受局部 intervention test，再成为 Candidate；
- IDEA-002R：机制先接受 Student realizability test，再被编译。

这两项本来就是 0820_report.md 中不可分割的前后半句。拆开以后，读者容易以为我们要在“先验证假设”和“先测 Student 能力”之间二选一。

第二，我为了防止过度 claim，把大量篇幅放在 Shepherd、HarnessBank、HASP 等最近邻工作的防御性边界上。这个边界是必要的，但它压住了真正的主叙事：我们改变的是 Harness Evolution 最早的实验单位和 credit-assignment boundary。

第三，我把 IDEA-005R 截止在 typed revision routing，没有继续追问“被打回的轨迹怎样成为下一轮可用、可修正的研究经验”。这使流程看起来能返工，却不会跨 Research Attempt 或 Evolution Run 学习。考虑当前已有设计文档、术语协议和 historical_experience 预留字段，这个省略过于保守。

## 2. 用一个具体例子解释整条主线

假设真实 Student rollout 暴露了一个失败：

> Student 看到两个来源的实体信息互相冲突，却直接生成最终答案。

Failure Analyst 先把问题限制为有界方向。Hypothesis Researcher 不直接写 Hook，而是提出：

> 当两个已读来源对目标实体给出冲突事实时，要求继续验证一次，可能减少无证据消解；如果无冲突样本也频繁触发，或重复 continuation 没有改善，这个假设就被否证。

确定性 Trial Selector 在观察任何新分支结果之前，从真实 Student rollout 中选择满足预注册条件的冻结 Prefix。对每个 Prefix 重新运行两臂：

1. no-op baseline continuation；
2. Teacher 施加一次只用于试验的 soft intervention，例如“当前两条证据冲突，请先验证再回答”。

这条 intervention 只是行为机制的实验臂。它不可部署、不能进入 Candidate pool，也不能携带可直接复制的完整 reusable guard/action patch。Teacher 没有在正式运行时替代 Student。

如果 repeated matched-prefix evidence 跨案例支持假设，我们再蒸馏机制：

> guard：存在目标实体的来源冲突；
> decision：positive / negative / uncertain；
> action：继续验证；
> fallback：uncertain 时不阻断正常流程；
> runtime inputs：来源实体、字段和冲突摘要。

接着才问第二个问题：固定 Student 能否稳定判断“冲突是否存在”，并正确执行 uncertain fallback？

- 如果能，机制可以由 Student-owned hook_model 承担；
- 如果不能，但冲突能由结构化字段确定，就改为 deterministic evaluator；
- 如果责任可以简化，就返回 Mechanism Distiller；
- 如果仍不可实现，就拒绝，不生成 Candidate。

只有通过这两道门，Compiler 才把机制固化为 Prompt、Hook、Tool、Parser 或其他 Candidate realization。Conformance 与完整 Candidate Evaluation 继续检查实现保真和全局效用。

因此，五个原候选可以用五个普通问题解释：

1. IDEA-001R：我们是否应该先做局部机制实验，再写持久化 Patch？
2. IDEA-002R：机制合理以后，小 Student 是否真的会判断并执行？
3. IDEA-003R：同一机制应该落成 Prompt、确定性 Hook、hook_model、Tool 还是 Parser？
4. IDEA-004R：局部实验怎样重复、配对和统计，才不把随机成功当成证据？
5. IDEA-005R：任一阶段失败以后，应回到哪里修改，并怎样把这次失败变成下一轮可用的经验？

其中 1 和 2 是同一主 IDEA 的两道核心门；4 是第一道门的测量协议；5 是跨阶段和跨 Run 的学习闭环；3 是条件性实现扩展。

## 3. 合并后的主研究方向

暂定名称：

Evidence-Gated Harness Evolution: Testing Mechanisms and Student Realizability Before Candidate Compilation

主研究问题：

> 对固定小模型 Student，我们先在真实 rollout 的冻结 Prefix 上用不可部署的局部干预检验行为假设，再将证据支持的机制与 Student 逐职责可实现性分开验证，之后才生成 Candidate；与 candidate-first evolution 相比，这个协议能否在严格预算匹配下提高 useful Candidate yield、减少无效完整评估，并改善失败归因？

主贡献边界：

1. Pre-compilation intervention testing：Harness Candidate 不再是最早实验对象。
2. Target-model realizability gating：正确机制不自动等于 Student 可执行机制。
3. Matched repeated prefix protocol：估计局部机制证据并检验它能否预测 downstream Candidate effect。

支持性边界：

- implementation-independent mechanism 与 conformance attribution boundary；
- typed revision routing；
- evidence-backed Research Experience 闭环。

我们不主张 Prefix-Fork、Teacher Agent、falsifiable hypothesis、Candidate gate、guard/action、multi-agent roles、typed trace 或 memory 本身首次出现。

## 4. 经验系统怎样进入最终方向

经验系统进入完整框架，但暂时不进入论文标题，也不与两道编译前门并列为主 novelty。它是 planned and evaluated supporting subsystem。

### 4.1 触发与确认

Reviewer 的 reject 或 revise 立即触发一个 deterministic Experience Candidate，只记录：

- producer role 与 consumer role；
- typed route 和 failure layer；
- revision obligation；
- hypothesis、mechanism 或 candidate fingerprint；
- scope、split、run 和 artifact refs。

Experience Candidate 不是长期事实。Experience Curator 在 Research Attempt、Candidate 或 Generation 结算点读取完整相关轨迹，才形成 provisional、confirmed、contradicted 或 superseded 的 Research Experience。后续修订结果可以确认、修正或反驳最初 Reviewer 的归因。

### 4.2 三个角色视图

三类内容共享同一规范化 Experience Record，不能成为三套互相冲突的摘要库。

Student 能力边界视图：

- 当前种子：Hook Feasibility probe、真实 Run 和 conformance artifacts；
- 计划能力：按 Student、Hook Model、Harness version、task family 和 responsibility scope 投影；
- 边界：普通 rollout 默认只能归因到 Student Agent，不能直接归因到 Student Model。

Teacher 角色工作经验视图：

- 当前种子：已经实现的 typed reject/revise route、obligation 和 role artifacts；
- 计划能力：总结上游输出怎样导致下游无法继续，以及什么信息必须保留或补充；
- 边界：目前没有 Curator、正式 Role Collaboration Experience 或投影机制。

已实验方向视图：

- 当前种子：events、artifacts、Candidate terminal status 和预算记录；
- 计划能力：Attempt Ledger、direction fingerprint、证伪状态、重试条件和去重；
- 边界：当前没有统一 Attempt Ledger，成功、失败和被后续推翻的判断都必须记录，不能只保存负面轨迹。

### 4.3 使用边界

历史经验只能提示“曾发生什么、当前应检查什么”。它不能：

- 补齐当前 Trial coverage；
- 直接通过或拒绝 Evidence/Feasibility/Promotion Gate；
- 永久禁止某个方向；
- 读取 held-out evaluator 私有信息；
- 让 Trial Worker 或 Reviewer 看见会污染当前独立判断的历史答案。

每个 Role Session 必须冻结 experience projection，并记录 retrieval/usage receipt。系统还要提供 bypass、contradiction、supersession 和抽样重试，以估计 false suppression。

## 5. 经验系统的独立消融

我们把经验因素与双门因素分开，避免把所有改动一次打开后无法归因。

经验对照：

1. No historical experience；
2. Unstructured rejection summary；
3. function-anchored、state-recalibrated historical evidence，作为 DREvo-like 最近邻；
4. typed evidence-backed role projection；
5. corrupted/stale experience stress test；
6. typed projection + bypass/recheck。

指标：

- duplicate direction rate；
- repeated failure 与 correction rounds；
- useful Candidate yield；
- total Teacher/Student tokens、wall-clock；
- experience retrieval 后角色输出改变率；
- 改变后的 downstream improvement；
- stale/incorrect experience 的 false suppression；
- contradiction、override 和 supersede 成功率。

经验实验以完整 Evolution Run 和 seed 为主要统计单位。Curator、检索和额外 Teacher tokens 全部计入预算。

如果结构化经验没有减少重复失败或成本，或者错误经验持续压制可行方向，我们就不声称它提高了研究效率。

## 6. 必须写入后续 Goal 的实现与实验条件

第一道门：

- 同一冻结 Prefix 必须重新运行 no-op control 与 intervention 两个 continuation；
- 两臂的 Student、温度、步数、工具和停止规则一致，并重复采样；
- 双臂执行顺序随机化或 blocked；prefix 重复和同一 example/trajectory 内的 continuation 不视为独立样本；
- hypothesis、适用范围、falsifier 和 Prefix 选择规则在分支结果前冻结；
- 预注册最少 case/example 覆盖、promotion threshold、harmful activation 上限、uncertainty 处理和 early stopping；
- 预先定义 Gate precision、false promotion 与 false rejection；
- 同时覆盖失败、成功和 near-miss Prefix；
- 抽样盲编译 Gate-rejected mechanisms，估计 false rejection。

第二道门：

- 责任范围不能只覆盖 decision_evaluator == hook_model；
- 独立标签不能复用蒸馏该机制的 Trial Reviewer 判断；
- mechanism、label calibration、feasibility、conformance 与 Candidate test Prefix 彼此隔离；
- 孤立 classification probe 之外，还要有不控制运行的 in-loop shadow execution；
- 主判据使用真实部署配置，即当前 Student thinking-off；其他 thinking mode 只作为预注册敏感性分析；
- 报告 recognition、adherence、fallback、parse failure 和 downstream utility。

完整系统：

- 做 Candidate-first、Evidence Gate only、Realizability Gate only、Evidence + Realizability 双门的因子消融；
- train、validation、held-out split firewall；
- Trial Worker、Evidence Reviewer 和 Feasibility labeler 不能读取 gold answer、held-out score、Judge 私有理由或未来 Candidate outcome；
- 以完整 Evolution Run / seed 比较最终效用、成本和 Candidate yield；
- 局部效应在 frozen prefix 上估计 paired continuation difference，并按 example/trajectory 聚类；使用 cluster bootstrap 或层级模型；
- 分开报告 local prefix estimand、mechanism-level estimand 和 Evolution-Run-level estimand；
- 用 held-out Candidate effect 检验 local-to-global 方向预测与 calibration；把 implementation conformance failure 与 mechanism transport failure 分开记账；
- 严格预算预留，禁止 soft limit 越界后继续声称公平；
- Candidate-first、Shepherd/HarnessBank-style screening、parallel sampling 和 sequential refinement 都必须作为预算匹配对照；
- useful Candidate 的定义必须预注册；
- 冻结 commit/tree、环境、数据 digest、Student、Teacher 与 Judge 配置；
- 增加第二 task family，或把所有外推结论限制在当前 retrieval/search harness 与任务分布。
